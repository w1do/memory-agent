# Дизайн: исправление таймаута `memory init`

Решение принято Sol (`SPEC: READY`). Источники фактов: сводка analyst и решение Sol. Ссылки `путь:строка` взяты из них; где сводки расходятся, указаны обе.

## Решения

### 1. Порядок работ

D1 → B1 → C1 / C2 → O1 → V1. A1 (учёт `.gitignore`) — отдельное изменение после V1.

Почему D первым: сейчас очередь фильтруется по пути, а чекпоинт продвигается даже при ошибках отдельных файлов ([src/indexing/sync.ts:81](src/indexing/sync.ts:81), [src/indexing/sync.ts:92](src/indexing/sync.ts:92)). Фоновый запуск без исправления D повторит эту ошибку в фоне. Исправления одной документации (README) недостаточно.

### 2. D1: безопасное возобновление

- Структурный этап при возобновлении строит очередь заново по manifest и ошибкам, без отсечения `path <= last_index_path`.
- Незавершённые записи повторяются идемпотентно.
- `last_index_path` показывает последнюю завершённую пачку (соответствует текущему README по смыслу после правки O1).
- Embedding продолжает выбирать чанки с `embedded = 0` ([src/indexing/embed-pending.ts:16](src/indexing/embed-pending.ts:16)); возобновление embedding не опирается на путь.

### 3. B1: разделение фаз

- `init` создаёт чанки, символы, связи и лексический индекс, но не вызывает embedding.
- `sync` (`memory sync`, `memory_sync`) продолжает строить векторы из pending-чанков.
- Единственное место построения векторов остаётся в sync-конвейере; `FileIndexer` векторы не создаёт ([src/indexing/file-indexer.ts:47](src/indexing/file-indexer.ts:47)).
- Текущая связь: `init` вызывает тот же `syncProject` ([src/cli/commands/init.ts:29](src/cli/commands/init.ts:29)), а тот всегда вызывает `embedPending` ([src/indexing/sync.ts:94](src/indexing/sync.ts:94)). B1 это меняет.
- Режим обработки и метка запуска разделяются: `init` выбирает структурный режим (structural), `sync` включает embedding. Метка `kind` (`init` / `sync`) остаётся для учёта, но не задаёт набор этапов сама по себе.

### 4. C1: фоновый запуск и контракт CLI/MCP

- C — основной механизм защиты от долгого ожидания. A и B уменьшают работу, но структурный этап тоже может превысить внешний таймаут, поэтому одного B недостаточно.
- По умолчанию `memory init` ставит структурный этап в независимый процесс и возвращает идентификатор задачи со статусом `accepted`.
- `accepted` возвращается только после: (а) сохранения задачи в manifest; (б) подтверждения запуска процесса. Ошибка запуска возвращается вызывающему.
- `accepted` не означает готовность индекса.
- `memory init --wait` ждёт завершения структурного этапа и возвращает результат. Это сохраняет совместимость для сценариев, которым нужен готовый индекс.
- `--no-index` сохраняется: отключает первичную индексацию. Поведение `--no-start` сохраняется ([src/cli/commands/init.ts:27](src/cli/commands/init.ts:27)).
- Фоновый процесс переиспользует те же этапы, что и синхронный путь; второго механизма индексации нет.
- Для embedding добавляется `memory sync --background` и `memory_sync(background: true)`. Синхронный `sync` остаётся совместимым.
- MCP-инструмент первичной инициализации не добавляется. Для первичной инициализации MCP-клиенту остаётся CLI или `memory_sync`.

Отвергнуто: простой shell-запуск с `&`. Нет надёжного подтверждения запуска, блокировки и состояния после падения.

### 5. C2: состояние задачи и конкуренция

- Задача сохраняется в manifest до сканирования: `id`, операция, состояние, этап, обработано / всего, `heartbeat`, ошибка, путь к очищенному от секретов логу.
- Состояния: `queued` → `running` → `completed` / `failed` / `interrupted`.
- `completed` допустим только при отсутствии ошибок соответствующей операции.
- На проект допускается один писатель индекса. Конкурирующая операция получает `busy` с идентификатором активной задачи.
- Повторный `init` присоединяется к активной инициализации.
- После падения повторный запуск возобновляет работу (см. D1).
- Быстрый режим статуса: `memory status --job <id>` / `memory_status(job_id)`. Только сохранённый прогресс; без обхода проекта и без сетевых health-check. Обычный `status` сейчас проверяет свежесть через сканирование ([src/project/status.ts:29](src/project/status.ts:29), [src/search/freshness.ts:15](src/search/freshness.ts:15)); это не меняется для обычного статуса.
- Падение worker обнаруживается по `heartbeat` и проверке владельца процесса.

Отвергнуто: автоматический embedding после фонового `init` (противоречит B1).

### 6. A1: учёт `.gitignore` (отдельное изменение)

- Вложенные `.gitignore`, отрицания и привязка шаблонов соответствуют Git.
- Встроенные запреты и `.memoryignore` нельзя отменить отрицанием.
- Должна быть возможность отключить учёт `.gitignore`.
- Лимит 512 KiB ([src/project/config.ts:18](src/project/config.ts:18)) сохраняется; произвольный предел числа файлов не вводится.
- Сейчас сканер читает только `.memoryignore` и встроенные исключения ([src/project/scan.ts:16](src/project/scan.ts:16); Sol указывает `scan.ts:15`), встроенные исключения — в [src/security/policy.ts:8](src/security/policy.ts:8).

Отвергнуто: молчаливая обрезка числа файлов. Это создаёт неполный индекс без понятного контракта.

### 7. O1 и V1

- O1: синхронизировать OpenSpec и README: описать `accepted` / `ready`, отдельный `sync`, повторение пачки, новые параметры и смену поведения `init`.
- V1: все unit-тесты проходят; стендовый замер `accepted` на контролируемом большом проекте; время полного индексирования измеряется отдельно.

### 8. E: MCP_TIMEOUT

Не решение. Допустимо только временно, после определения вызывающего клиента. CLI `init` не является MCP-вызовом, поэтому универсальность настройки не подтверждена.

## Отвергнутые варианты (сводка)

| Вариант | Причина отказа |
|---|---|
| Только A или только B | Не ограничивают длительность оставшегося структурного этапа |
| C как shell `&` | Нет подтверждения запуска, блокировки и состояния после падения |
| D только в документации | Оставляет риск пропуска файлов; исправляется поведение и описание |
| E как решение | Не подтверждено для CLI; внешний таймаут не установлен |
| Автоматический embedding после фонового init | Противоречит B1 |
| Молчаливая обрезка файлов | Неполный индекс без контракта |

## Не проверено

- Точный внешний таймаут вызывающей среды.
- Место прежнего обрыва.
- Расхождения номеров строк: `init.ts:29` (analyst) и `init.ts:35` (Sol); `scan.ts:16` (analyst) и `scan.ts:15` (Sol); `shared-init.test.ts` упомянут в сводках, но его содержимое не читалось.
- Работа фонового процесса при уничтожении группы процессов средой.
- Полная политика сроков хранения логов задач: не реализована, вне объёма.
- Поведение логов на платформах вне Linux в реальной среде: не проверено.

## Риски

- Изменение состава индекса при A1: ранее включённые документы могут быть удалены при `sync`. Поэтому A1 отдельно и с отключением.
- Новое значение `init` при успешном возврате: сценарии, которым нужен готовый индекс, используют `--wait`.
- Запуск сервисов может задержать `accepted`: длительные проверки и запуск выполняются внутри фоновой задачи.

## Детали реализации (O1)

- Задачи хранятся JSON-записями `index_job:<uuid>` и ссылкой `active_index_job` в существующей таблице `meta`; миграция схемы не требуется. Резервирование писателя выполняется в SQLite `BEGIN IMMEDIATE`. Тот же lease используют sync-конвейер и точечные обновления (CLI, MCP, watch).
- `kind` остаётся меткой запуска; `mode: structural | full` независимо выбирает фазы. Worker init передаёт structural, sync — full. `FileIndexer` не строит векторы. Статус отдельно возвращает `pending_embeddings`.
- Независимый worker подтверждает запуск через IPC до проверки сервисов и обхода проекта. Родитель отключает IPC и освобождает ссылку на дочерний процесс. Ошибка или отсутствие подтверждения за 8 с возвращается вызывающему; worker останавливается до освобождения писателя.
- UUID задачи, operation, state, stage, processed/total, heartbeat, error, log_path и владелец сохраняются до сканирования. Лог `.memory/logs/job-<uuid>.log` записывается через Logger с redaction; сырой stdout/stderr дочернего процесса не сохраняется. Лог-файл создаётся только на Linux; на других платформах `log_path` = `null`, `log_unavailable_reason` = `unsupported_platform`.
- Ротация: хранятся последние 50 завершённых задач (`completed`, `failed`, `interrupted`). Активная и текущая задача не удаляются; их логи удаляются вместе с записью. Полная политика сроков хранения не реализована (вне объёма).
- `memory sync --background` без ключа эмбеддингов завершает задачу как `failed` из-за `semanticError`. Это зафиксировано в приёмке как поведение; см. `specs/job-status/spec.md`.
- Heartbeat обновляется раз в секунду. При возрасте от 30 с проверяются существование владельца и, на Linux, время старта PID. Исчезновение или подмена владельца переводит задачу в interrupted; живой владелец сохраняет lease даже при задержке heartbeat во время синхронного сканирования.
- `accepted` означает сохранённую и запущенную задачу; готовность (`ready`) структурного индекса — completed. `--wait` ждёт итог и сохраняет пробный лексический поиск. `--no-start` и `--no-index` сохраняют исходное условие запуска индексации `start && index`.
- Обычный status сохраняет health-check и проверку свежести. Режим job читает manifest без открытия клиентов, matcher и проверки свежести.
- Чекпоинт показывает завершённую пачку и не продвигается после ошибки. Повторяются только отсутствующие, изменённые и ошибочные записи; существующие успешные записи не дублируются.

Исходные номера строк сверены по HEAD: вызов syncProject из init был на строке 35, отсечение по курсору — sync.ts:83–84, продвижение курсора — sync.ts:98, embedding — sync.ts:101. Ссылки из аналитических сводок выше являются историческими.
