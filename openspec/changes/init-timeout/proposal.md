# Исправление таймаута `memory init` на больших проектах

Status: Implementation pending validation
Code: D1, B1, C1, C2 реализованы; проверки блокирует недоступный guards.lock. A1 не входит в изменение.

## Проблема

До изменения (проверено по исходному HEAD) `memory init --path <dir>` работает синхронно:

- CLI вызывает `initCommand` ([src/cli/index.ts:33](src/cli/index.ts:33)); при стандартных `--start` и `--index` команда открывает контекст и ждёт весь `syncProject(ctx, { kind: 'init' })` (в исходном HEAD вызов на `src/cli/commands/init.ts:35`; ссылка из сводки на `:29` неточна).
- `syncProject` всегда включает embedding: `embedPending` вызывается из `syncProject` (в исходном HEAD `src/indexing/sync.ts:101`). Значит, `init` ждёт и структурную индексацию, и внешний embedding API.
- Общего таймаута на цепочку `init` / `syncProject` в коде нет. У запроса к embedding API задан таймаут 30 секунд на запрос ([src/embeddings/openai.ts:47](src/embeddings/openai.ts:47)); у Typesense `connectionTimeoutSeconds: 5` ([src/storage/typesense.ts:37](src/storage/typesense.ts:37)). Внешний таймаут, на который натыкается пользователь, по коду не определён.
- Сканер обходит весь корень проекта и не читает `.gitignore`: он читает `.memoryignore` и использует встроенные исключения ([src/project/scan.ts:16](src/project/scan.ts:16)). Лимит размера файла по умолчанию 512 KiB ([src/project/config.ts:18](src/project/config.ts:18)). Каталоги, которые Git игнорирует, но встроенные исключения и `.memoryignore` не покрывают, тоже обходятся. Какая доля объёма приходится на них, не проверено.
- Сканирование, `stat`, хеширование и чтение файла выполняются синхронно ([src/project/scan.ts:34](src/project/scan.ts:34)); обработка файла пишет чанки, символы, связи и документы в Typesense ([src/indexing/file-indexer.ts:47](src/indexing/file-indexer.ts:47)).
- Прерванный запуск не оставляет понятного состояния: `last_path.indexing` и `last_path.embedding` в переданном снимке статуса равны `null` ([сводка analyst](/home/dev/.claude/codex-tasks/memory-agent/init-timeout/1-analyst.result.md)).
- Чекпоинт `last_index_path` продвигается после пачки, а README описывает продолжение «с этого файла» ([README.md:40](README.md:40)). Код продолжает с последней завершённой пачки и фильтрует очередь по сравнению путей ([src/indexing/sync.ts:92](src/indexing/sync.ts:92)). Сводка Sol указывает, что чекпоинт продвигается и при ошибках отдельных файлов ([src/indexing/sync.ts:81](src/indexing/sync.ts:81)). Это значит, что повторный запуск может пропустить файлы.

## Цель

- `memory init` возвращает управление за короткое время (целевой ориентир из плана Sol: `accepted` меньше 10 с на контролируемом большом проекте при готовом общем сервисе). Фактическое время пока не измерено.
- Структурная индексация (чанки, символы, связи, лексический индекс) выполняется в фоновой задаче с сохранённым состоянием.
- Embedding отделён от `init` и запускается только через `sync` (`memory sync` / `memory_sync`). Правило «векторы строит только sync-конвейер» сохраняется.
- Прерванная задача безопасно продолжается: файлы, которые не были записаны, не теряются и не индексируются повторно без необходимости.
- Ошибки не маскируются: состояние `completed` возможно только при отсутствии ошибок.

## Что не входит в объём

- Новый MCP-инструмент первичной инициализации (`memory_init`). Для MCP остаётся `memory_sync` с параметром `background`.
- Автоматический embedding после фонового `init`.
- Молчаливое ограничение числа файлов (произвольный предел не вводится). Лимит размера 512 KiB не меняется.
- Изменение формата `.memory/index.db` без отдельной миграции.
- Изменение хранения и поиска (hybrid, lexical, semantic).
- Увеличение `MCP_TIMEOUT` как решение. Настройка клиента допустима только как временная мера после определения вызывающей среды; её универсальность не подтверждена.
- Учёт `.gitignore` выпускается отдельным изменением (см. `specs/ignore-policy`), потому что меняет состав индекса.

## Предлагаемое решение

Подробности и отвергнутые варианты — в `design.md`. Кратко:

1. D1: безопасное возобновление (чекпоинт не пропускает ошибки и изменения).
2. B1: разделение фаз. `init` строит структурный индекс без embedding; `sync` строит векторы.
3. C1, C2: фоновый запуск структурного этапа, контракт CLI/MCP (`accepted`, `--wait`), один писатель, состояние задачи в manifest.
4. O1: синхронизация OpenSpec и README.
5. V1: итоговая проверка контракта и замер времени.
6. A1: учёт `.gitignore` отдельным изменением после V1, с возможностью отключения.

## Критерии приёмки

- `memory init` без `--wait` возвращает `accepted` после сохранения задачи и подтверждения запуска процесса; на контролируемом большом проекте это занимает менее 10 с при готовом общем сервисе (замер не проведён).
- `memory init --wait` возвращает результат только после завершения структурного этапа.
- `init` не вызывает embedding ни разу.
- После остановки задачи повторный `init` продолжает работу и не теряет файлы, которые не были записаны.
- Быстрый `memory status --job <id>` не сканирует проект и не делает сетевых health-check.
- Все unit-тесты из `tasks.md` проходят (команды в `tasks.md`, сейчас не запускались).

## Риски

- Среда может уничтожать всю группу процессов или контейнер при завершении родителя. Фоновый процесс в этом случае не переживёт родителя. Это проверяется в целевом окружении (V1), а не увеличением таймаута.
- Новый `init` меняет значение успешного возврата: сценарии, которым нужен готовый индекс, должны использовать `--wait`.
- Учёт `.gitignore` меняет состав индекса. При последующем `sync` ранее включённые документы могут быть удалены. Поэтому A1 выпускается отдельно и с возможностью отключения.
- Точный внешний таймаут и место прежнего обрыва не установлены (см. раздел «Не проверено»).

## Не проверено

- Точный внешний таймаут вызывающей среды (клиента или оболочки). Конфигурация клиента в репозитории не найдена; по коду определить нельзя.
- Место прежнего обрыва: нет лога конкретного запуска. Снимок статуса с `last_path.indexing = null` и `last_path.embedding = null` не показывает зафиксированной точки.
- Фактическое время `accepted` и полного индексирования: не измерялось.
- Поведение `init` и фоновой задачи в среде, где группа процессов уничтожается при выходе родителя: не проверено.
- Расхождения номеров строк между сводками: `init.ts:29` (analyst) и `init.ts:35` (Sol); `scan.ts:16` (analyst) и `scan.ts:15` (Sol). Перед реализацией сверить по коду.

## Реализация и границы проверки

`init` запускает структурный worker, `--wait` ждёт его итог. `accepted` с `job_id` подтверждает запуск, готовность (`ready`) структурного индекса означает `completed`. Embedding запускается отдельно через `sync` / `memory_sync`, в том числе с `--background` / `background: true`. Быстрый статус: `status --job` / `memory_status(job_id)`. Возобновление повторяет незавершённые записи пачки по manifest и ошибкам, без фильтра путей по `last_index_path`.

Проверка TypeScript прошла (exit 0). Команды unit-тестов пока не запускались: обязательный `flock ~/.claude/codex-tasks/memory-agent/guards.lock …` завершается с exit 73, Read-only file system. Стендовые замеры и уничтожение группы процессов не проверены. Успешные проверки не заявляются до фактического запуска.
