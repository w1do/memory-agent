## Проблема

Сейчас `memory init` в каждом проекте:

- создаёт свой `.memory/docker-compose.yml` с отдельными контейнерами `memory-<collection>-qdrant` и `memory-<collection>-typesense`;
- выделяет свои порты (`qdrantPort`, `typesensePort` в `.memory/config.json`);
- хранит свой `.memory/.env` с `TYPESENSE_API_KEY` и `EMBEDDING_API_KEY`;
- держит свои данные в `.memory/data`.

При десятках проектов это даёт десятки пар контейнеров, дублирование ключей и embeddings-настроек, конфликты портов и ручную настройку в каждом репозитории. Пользователь хочет один раз поднять и настроить сервис, а в проектах выполнять только `memory init`.

## Цель

- Один общий стек Qdrant + Typesense (и один набор секретов) поднимается один раз на машине.
- Проект получает изоляцию данных через коллекции, а не через отдельные контейнеры.
- `memory init` в проекте не запускает Docker, если общий сервис уже доступен, и только регистрирует проект.
- Все проекты работают через один MCP-сервер или через MCP с параметром проекта.

## Не цели

- Не строить свой backend, CMS или систему аутентификации поверх сервиса.
- Не менять формат манифеста `.memory/index.db` без отдельной миграции.
- Не переписывать поиск (hybrid/lexical/semantic) — только место, где живут сервисы.

## Предлагаемое решение

### 1. Глобальная конфигурация (`~/.config/project-memory/`)

- `global.env` — `TYPESENSE_API_KEY`, `EMBEDDING_BASE_URL`, `EMBEDDING_API_KEY`, `EMBEDDING_MODEL`, `EMBEDDING_DIMENSIONS`.
- `docker-compose.yml` — один стек с фиксированными портами по умолчанию (`127.0.0.1:6333`, `127.0.0.1:8108`) и healthcheck.
- Команда `memory service up|down|status|logs` управляет только этим стеком.

Файл `global.env` не попадает в Git проектов, права доступа `600`.

### 2. Проект

- `memory init` создаёт `.memory/config.json` и `.memory/.ignore`, коллекцию `<slug>-<hash>` в общем Qdrant/Typesense, но не создаёт свой compose.
- В `.memory/.env` остаётся только локальное переопределение (необязательно).
- Если сервис не запущен, `memory init` сообщает: `memory service up` и не падает молча.

### 3. MCP

- Один глобальный MCP-сервер (`memory mcp`) регистрируется у клиента один раз.
- Инструменты получают `project` (путь или имя коллекции), по умолчанию определяется по текущему каталогу.
- Альтернатива: отдельный MCP-процесс на проект с общими сервисами — проще для клиентов без поддержки параметров.

### 4. Изоляция и безопасность

- Все сервисы слушают только `127.0.0.1`.
- Коллекция — граница данных проекта; запрос без проекта не выбирает чужие коллекции.
- Ключи и тексты embeddings не логируются; в аудит попадают только префикс и последние 4 символа ключа.

### 5. Миграция

- `memory migrate` переносит существующие `.memory/data` или пересоздаёт коллекцию через `memory reindex`.
- Старые проекты продолжают работать, пока не выполнена миграция (обратная совместимость на один релиз).

## Критерии приёмки

- Один `memory service up` поднимает Qdrant и Typesense на всей машине; повторный запуск идемпотентен.
- Два проекта на одной машине индексируются в разные коллекции и не видят файлы друг друга.
- `memory init` в третьем проекте не создаёт контейнеров и занимает меньше 10 секунд при запущенном сервисе.
- Без `EMBEDDING_API_KEY` поиск работает в degraded lexical mode, как сейчас.
- `memory doctor` показывает состояние общего сервиса и отдельно состояние проекта.
- Тесты покрывают: идемпотентность `service up`, изоляцию коллекций, поведение при остановленном сервисе.
- Каждый файл с кодом не длиннее 150 строк (предпочтение пользователя).

## Риски

- Общий сервис — единая точка отказа для всех проектов; нужен `memory service status` и понятные ошибки.
- Смена модели embeddings влияет на все проекты сразу; нужна проверка размерности при init.
- Конфликт портов с другими сервисами на машине; нужна переменная порта в `global.env`.
- Типичный `docker compose` с `name:` на один стек упрощает управление, но требует миграции имён контейнеров.

## Принятые решения (по ответу пользователя)

- Qdrant, Typesense и база поднимаются один раз на машине одним стеком (`memory service up`).
- Глобальный MCP: один процесс `memory mcp`, проект определяется по текущему каталогу.
- Миграция по умолчанию через `memory reindex` (данные не переносим, это проще и надёжнее).
- Только localhost; удалённый сервис вне рамок этой версии.
- Манифест `index.db` (кэш индекса) переносится в глобальное хранилище `~/.config/project-memory/index/<projectId>/index.db`; общий сервис хранит только коллекции Qdrant/Typesense.
- Аннотации (`memory_annotate`) — единственные данные, которые нельзя восстановить переиндексацией, поэтому они хранятся в проекте в `.memory/annotations.json` и могут коммититься.
- Привязка проекта к кэшу — `projectId` в `.memory/config.json`; перемещение репозитория не ломает привязку.
- В проекте остаются только `.memory/config.json`, `.memory/.ignore`, `.memory/annotations.json` и необязательный `.memory/.env`.

## Миграция уже существующих `.memory` (много проектов)

Что есть в старом проекте: `.memory/config.json` (порты, коллекция), `.memory/docker-compose.yml`, `.memory/.env`, `.memory/data` (Qdrant/Typesense), `.memory/index.db`.

### Команды
- `memory migrate` — один проект: определяет старый формат по наличию `.memory/docker-compose.yml`, мигрирует на месте.
- `memory migrate --scan <каталог>` — находит все `.memory/` под каталогом, показывает список (dry-run по умолчанию); `--apply` выполняет.
- `memory migrate --all` — по реестру проектов `~/.config/project-memory/projects.json` (заполняется при `init`/`migrate`).

### Шаги миграции одного проекта
1. Проверка: общий сервис запущен (`memory service status`), иначе подсказка `memory service up` и остановка.
2. Бэкап: `.memory/` копируется в `.memory.bak-<дата>` (кроме `data`, если она большая; `index.db` и `config.json` копируются всегда).
3. Остановка старых контейнеров проекта: `docker compose -f .memory/docker-compose.yml down` (данные не удаляются).
4. Секреты: если `global.env` пуст, значения `EMBEDDING_*` берутся из первого найденного `.memory/.env`; при расхождении ключей между проектами — предупреждение и выбор пользователя. `TYPESENSE_API_KEY` проекта больше не нужен.
5. `config.json`: удаляются `qdrantPort`/`typesensePort`, добавляется `schemaVersion: 2` и имя коллекции `<slug>-<hash>` (старое имя сохраняется, если совпадает).
6. Переиндексация в общий сервис: `memory reindex` читает файлы проекта и создаёт коллекции; `index.db` переиспользуется, чтобы не переэмбеддить неизменённые файлы, если модель и размерность совпадают.
7. Проверка: `memory doctor` + контрольный поиск; только после успеха старые `docker-compose.yml`, `.env`, `data` удаляются (с `--cleanup`, по умолчанию остаются).
8. Откат: `memory migrate --rollback` восстанавливает из бэкапа и поднимает старый compose.

### Требования
- Идемпотентность: повторный `migrate` на уже мигрированном проекте — no-op.
- Ошибка в одном проекте не прерывает пакетную миграцию; итоговый отчёт: успех / пропущено / ошибка.
- Разные embeddings-модели в проектах: проект с другой размерностью получает отдельный суффикс коллекции или требует полной реиндексации (явное предупреждение).
- Старые проекты работают без миграции один релиз (совместимость), `memory doctor` подсказывает `memory migrate`.
- Критерии приёмки: тест миграции фикстуры старого проекта, идемпотентность, откат, пакетный режим с одной сломанной папкой.
